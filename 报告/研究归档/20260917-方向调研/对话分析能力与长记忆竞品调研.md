# 对话分析能力、对比分析与长记忆竞品调研

日期：2026-09-17

## 一、调研结论

主流分析产品的共同路线不是“把大模型接到数据库上”，而是：

```text
治理语义层
-> 自然语言意图映射
-> 标准化分析模式
-> 自动选择可视化
-> 保留对话和业务上下文
-> 生成可追溯的报告或分析结果
```

对比只是其中一种分析模式。完整能力至少还包括趋势、结构、分布、排名、贡献、归因、异常、相关性、分层、基准、情景模拟和下钻。

## 二、公开来源

1. Microsoft Copilot for Power BI
   - https://learn.microsoft.com/en-us/power-bi/create-reports/copilot-introduction
   - 要点：使用前需要准备语义模型；支持聊天分析、报告摘要、创建可视化；清理聊天气泡会清除当前对话上下文；相同模型和相同问题在缓存窗口内复用结果。

2. Amazon Quick 用户指南
   - https://docs.aws.amazon.com/quicksight/latest/user/quicksight-q.html
   - 要点：自然语言聊天、连接结构化数据、交互式可视化、研究报告和基于组织数据回答。

3. Databricks Genie
   - https://docs.databricks.com/aws/en/genie/
   - 要点：Genie Agents 由数据团队配置受信任的数据、指标和业务规则；回答受治理数据约束；支持自然语言问数和后续探索。

4. Cube Semantic Layer
   - https://cube.dev/docs/product/semantic-layer
   - 要点：集中管理指标定义、维度、Join、权限和缓存；AI Agent 查询 Semantic SQL，而不是直接写未经治理的仓库 SQL。

5. dbt MetricFlow
   - https://docs.getdbt.com/docs/build/about-metricflow
   - 要点：用 YAML 定义语义模型、指标、维度和时间粒度，强调 DRY、一致性和跨 BI/Agent 复用。

6. LangGraph Memory
   - https://docs.langchain.com/oss/python/langgraph/add-memory
   - 要点：短期记忆是线程级 checkpoint；长期记忆跨会话保存；支持语义搜索、裁剪消息、摘要消息和检查点管理。

## 三、完整分析模式矩阵

| 分析模式 | 用户常见说法 | 需要的语义 | 推荐可视化 | 后续追问 |
|---|---|---|---|---|
| 对比 | 和去年比、和同行比、A和B比 | 指标 + 两个范围 + 时间对齐 | 分组柱状图、斜坡图 | 差异来自哪里 |
| 趋势 | 最近怎么样、有没有变差 | 指标 + 时间粒度 + 时间范围 | 折线图、面积图 | 哪一段变化最大 |
| 结构 | 主要由什么构成 | 指标 + 分类维度 + 占比 | 堆叠柱状图、环形图 | 哪个分类贡献最大 |
| 分布 | 都集中在哪些区间 | 指标 + 分箱 + 分组维度 | 直方图、箱线图 | 异常值是谁 |
| 排名 | 哪几家最高、前10是谁 | 指标 + 排名方向 + 范围 | 横向条形图、排行榜 | 第一名为什么高 |
| 贡献 | 为什么总额变化 | 指标 + 分解项 + 时间/范围 | 瀑布图、贡献条形图 | 哪个因素拖累最大 |
| 归因 | 为什么风险升高 | 指标关系 + 业务规则 + 因子 | 贡献图、桑基图、路径图 | 能否下钻到明细 |
| 异常 | 哪里不对劲 | 指标分布 + 阈值/基线 | 散点图、异常矩阵 | 异常是否持续 |
| 相关性 | 两个指标有没有关系 | 双指标 + 样本 + 分组 | 散点图、相关系数 | 是否存在因果 |
| 分层 | 哪类企业风险最高 | 分类维度 + 风险指标 | 热力图、矩阵图 | 哪个细分最异常 |
| 基准 | 和行业标准差多少 | 主体指标 + 同行基准 | 条形图、雷达图 | 差距来自哪个指标 |
| 情景模拟 | 如果下降10%会怎样 | 指标 + 参数 + 假设 | 条形对比、情景曲线 | 哪个假设最敏感 |
| 下钻 | 这个异常由什么组成 | 当前 Claim + 明细粒度 | 明细表、瀑布图 | 继续拆到订单/月度 |
| 报告 | 把这些结论组成报告 | Case + Claim + 章节 | Block 组合预览 | 调整章节顺序 |

## 四、对比分析的标准解法

对比分析不是简单把两个数字相减，而是要明确五个槽位：

```text
指标
当前范围
对比范围
时间口径
对比方式
```

对比方式至少有：

- 环比
- 同比
- 同行对比
- 行业基准对比
- 目标值对比
- 个体之间对比
- 群体切片对比
- 结构贡献对比

回答结构应固定为：

```text
结论：谁高、谁低、差多少
依据：差值、变化率、区间和样本量
解释：主要差异来自哪些指标
边界：样本是否足够、口径是否一致
下一步：继续拆行业、时间、主体或生成报告
```

## 五、主流产品的共同机制

### 1. 语义层是底座

Power BI、Quick、Databricks Genie、Cube 和 dbt MetricFlow 都不让 AI 直接随意生成事实数字。

共同结构：

```text
指标定义
+ 维度
+ 时间粒度
+ 过滤条件
+ 权限
+ 业务规则
```

这正好对应我们现有的指标注册表、阈值和 Tool Registry，但需要增加分析模式和分析任务。

### 2. 自然语言先转成结构化分析任务

不是直接变成 SQL，而是先得到：

```text
metric
scope
comparison_target
time_range
dimension
analysis_type
visualization_type
```

### 3. 可视化由分析模式决定

主流产品会自动给出适合当前问题的视觉表达：

- 对比：分组柱状图或斜率图
- 趋势：折线图
- 构成：堆叠图或环形图
- 贡献：瀑布图
- 分布：直方图或箱线图
- 多维评分：雷达图
- 关联：散点图
- 分层：热力图

我们的系统不应只返回一张偶然出现的图表，而应返回 `visuals[]`。

### 4. 记忆分为两层

LangGraph 的定义和主流产品实践一致：

```text
短期记忆：当前 thread 的消息、状态、检查点
长期记忆：跨会话的用户偏好、实体、案例和知识
```

长记忆不是缓存整个聊天记录，而是保存可检索的 Case、Topic 和 Claim 引用。

### 5. 报告由治理后的结果组装

报告不是重新问一次 LLM，而是：

```text
Case 集合
+ Claim
+ 图表
+ 章节 Block
+ 报告模板
```

这与我们现有的报告 Block 模型方向一致，但需要补 Case 和语义去重。

## 六、映射到我们的系统

### 需要新增的契约

```text
ConversationCase
AnalysisPattern
VisualizationPlan
ReportBlockFingerprint
```

### ConversationCase 负责

- 主体、行业、范围
- 指标组合
- 分析模式
- Claims 和图表
- 原始问题与结论
- 报告引用

### AnalysisPattern 负责

- 对比、趋势、结构、分布、排名、贡献、归因、异常、相关、分层、基准、模拟、下钻
- 每个模式需要的槽位
- 每个模式的校验规则
- 每个模式的默认可视化和下钻动作

### VisualizationPlan 负责

- 根据分析模式生成多张图
- 图表与 Claim 绑定
- 图表可进入对话或报告

### ReportBlockFingerprint 负责

- 识别重复指标和重复结论
- 保证同一 Claim 只在一个主块出现
- 章节只引用 Block，不复制 Block

## 七、我们现在的差距

1. 当前主要是“指标查询 + 单图表”，没有完整分析模式注册表。
2. 行业还没有成为一等范围状态。
3. 对话响应只保留一个 chart，缺少 `visuals[]`。
4. 长期记忆有入口，但 Case 和结论锚点还不够结构化。
5. 报告和对话共用 Claim，但没有共用 AnalysisPattern。
6. 报告 Block 还没有语义去重指纹。
7. 用户不知道下一步看什么，因为系统没有按分析模式生成“下一步动作”。

## 八、建议的实施优先级

1. 建立 AnalysisPattern Registry。
2. 建立 ConversationCase 和 Topic Resolver。
3. 把范围和行业纳入对话状态。
4. 输出 `visuals[]`，不再只有一个 `chart`。
5. 按 Case 和 Claim 生成报告章节。
6. 给报告 Block 加语义指纹和去重。
7. 增加跨话题追问、对比追问、行业追问和报告复用测试。

## 九、最终判断

我们不应该继续扩展“聊天式回答”，而应该建设一个：

```text
分析模式驱动的对话式风控工作台
```

用户提出目标，系统识别分析模式，组合指标和范围，执行确定性 Claim，自动选择可视化，并允许将结果变成报告章节。这是比单纯扩大 RAG 指标库更重要的下一步。
