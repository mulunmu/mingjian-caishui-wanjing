# 上市公司财报、舆情与数据采集方案调研

日期：2026-09-17

## 一、结论

上市公司/行业风险分析需要舆情，但不能把它简化为“新闻正负面情感”。

应分成两层：

```text
第一层：披露事件和风险信号抽取
第二层：新闻、公告、研报和市场情绪分析
```

财报字段提取比新闻抓取更重要，也更困难。不能只做 PDF 全文下载，必须做到：

```text
文件来源可追溯
字段值可定位
表格可校验
多个来源可交叉验证
```

## 二、舆情是否必需

对金融风险模型而言，舆情是重要特征，但不是第一天就必须成为主模型。

优先抽取：

- 持续经营风险
- 资产减值
- 商誉减值
- 相关方交易
- 对外担保
- 债务违约
- 诉讼仲裁
- 监管处罚
- 审计意见变化
- 管理层变动
- 会计差错更正
- 业绩预告修正

这些是结构化事件，比“新闻情绪是正还是负”更可靠。

新闻情绪适合第二阶段，必须处理：

- 重复转载
- 时间错配
- 来源可信度
- 主体识别
- 事件因果和事实/观点分离

## 三、财报数据的可行采集范围

不要一开始抓取全部公告。

第一阶段只抓：

```text
年度报告
半年度报告
季度报告
业绩预告
业绩快报
审计意见相关公告
重大风险公告
```

按公司数量估算：

```text
500 家 × 4 份/年 × 3 年 ≈ 6000 份报告
```

这个规模个人研究者是可以处理和分析的。  
如果一开始抓全市场所有公告，数据量、去重和解析成本会迅速失控。

## 四、数据源优先级

1. 交易所和监管机构官方公开信息。
2. 公司官网投资者关系页面。
3. SEC EDGAR / 官方 XBRL API。
4. CNINFO、SSE、SZSE 等公开公告页面。
5. Tushare、AKShare 等便利型工具。
6. 合法公开新闻和公开行业数据库。

付费 API 不做核心依赖，只允许未来作为可选补充。

## 五、爬虫不是单脚本，而是一条流水线

```text
Source Registry
-> Discovery
-> Download
-> Parse
-> Extract
-> Validate
-> Store
-> Schedule
```

### Source Registry

记录数据源、授权、入口、更新频率、限速、文件类型、使用条款和负责人。

### Discovery

先抓元数据，不先下载全文：

```text
公司
报告类型
报告期
发布时间
公告链接
文件格式
来源
```

### Download

- URL 去重。
- 文件哈希去重。
- 断点续传。
- 限速和重试。
- 失败记录。

### Parse

优先级：

```text
结构化 XBRL/HTML
-> 原生 PDF 文本和表格
-> OCR
```

PDF 主要处理：

- 文本层
- 表格边界
- 跨页表格
- 页眉页脚
- 数字单位
- 括号表示的负数
- 千分位和百分比

### Extract

字段抽取必须使用 Schema，而不是直接让 LLM自由作答：

```text
公司身份
报告期
报表类型
数值
单位
币种
页码
原始文本片段
抽取方法
置信度
```

### Validate

至少做四层校验：

1. 数值范围校验。
2. 会计恒等式校验。
3. 同比和环比异常校验。
4. 多来源交叉校验。

## 六、可用工具

可组合使用：

- `pdfplumber`：文本和表格。
- `PyMuPDF`：页面和文本坐标。
- `Docling`：文档结构和版面解析。
- `MinerU`：复杂 PDF 版面与内容提取。
- `PaddleOCR` / Tesseract：扫描件 OCR。
- `Pydantic`：抽取结果 Schema。
- LLM 结构化提取：作为规则和表格解析的补充，不作为唯一事实来源。

原则：

```text
先规则和结构化源
再表格解析
最后 LLM 补足
所有字段必须保留证据位置
```

## 七、舆情和事件抽取

第一阶段建议使用固定事件标签：

```text
going_concern
impairment
related_party
guarantee
litigation
regulatory_penalty
debt_default
auditor_change
management_change
restatement
earnings_warning
```

第二阶段再增加：

- 新闻情感。
- 研报观点。
- 管理层语气。
- 风险披露变化。
- 事件时间线。

## 八、验证方案

先用小样本做真实验证：

```text
10 家公司
3 年
年度/半年度/季度报告
业绩预告和重大公告
```

记录：

- 下载成功率。
- PDF 解析成功率。
- 表格识别成功率。
- 字段抽取准确率。
- OCR 触发率。
- 单个报告平均耗时。
- 人工校验耗时。
- 失败类型。

只有通过验证，才能把采集器接入 Domain Pack。

## 九、推荐架构

```text
Object Storage
  原始 PDF / HTML / XBRL

PostgreSQL
  文件元数据、任务、版本、来源

Analytical Store
  标准化财务事实

Vector Store
  报告章节和事件片段

Domain Pack
  指标、维度、阈值、分析模式、报告模板
```

## 十、实施顺序

1. 先做一个交易所和 10 家公司的垂直试点。
2. 只抓核心报告。
3. 先做文本和表格解析。
4. 再抽取核心财务字段。
5. 引入会计恒等式和交叉校验。
6. 将结构化财务事实接入现有 Claim。
7. 再增加披露事件抽取。
8. 最后增加新闻舆情和预测特征。

## 十一、最终判断

真正难的从来不是“把 PDF 下载下来”，而是：

```text
解析
字段定位
表格校验
来源追溯
增量更新
```

因此后期转型应以“财报数据契约”为起点，而不是先写全市场爬虫。只要先在一个交易所和少量公司上验证成功，就可以证明上市公司/行业风险方向的数据链路是可落地的。
