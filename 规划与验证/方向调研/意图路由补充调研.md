# 意图路由补充调研与后台实测

日期：2026-09-18

## 调研来源

1. Rasa 3.x Components
   - 来源：https://legacy-docs-oss.rasa.com/docs/rasa/components/
   - 关键机制：NLU pipeline 按顺序把用户输入变成结构化 output；DIET 同时做意图分类和实体抽取；FallbackClassifier 在最高意图置信度不足，或前两名意图得分过于接近时触发 `nlu_fallback`。
   - 对项目的启示：意图识别不能只看单一标签，必须同时保留置信度、候选意图和歧义状态。

2. Rasa Policy Overview
   - 来源：https://rasa.com/docs/rasa/policies/
   - 关键机制：每个 policy 预测下一步 action，并给出 confidence；最终由置信度最高的 policy 决定下一步，低置信度可以拒绝预测。
   - 对项目的启示：路由不应只有一个固定规则命中，应该允许“分析路线、澄清路线、非分析路线、拒绝路线”竞争。

3. LangGraph Graph API
   - 来源：https://docs.langchain.com/oss/python/langgraph/graph-api
   - 关键机制：以 StateGraph 管理状态，normal edge 与 conditional edge 决定流向；节点可以返回 `Command` 更新状态并跳转；checkpoint 支持恢复执行。
   - 对项目的启示：路由应作为状态机中的显式节点，而不是散落在服务内部的 if/else；行业、实体、场景、分析模式都应该属于状态。

4. Anthropic Building Effective Agents
   - 来源：https://www.anthropic.com/engineering/building-effective-agents
   - 关键机制：Routing 先分类再交给专门任务；适用于类别相对清晰、分类准确率足够的场景。Orchestrator-workers 适合无法预先确定子任务的复杂请求。
   - 对项目的启示：普通问题和明确分析走 routing；多行业、多指标、开放分析走 orchestrator + workers + synthesis。

## 对当前系统的直接结论

- 12 路路由不够，是因为路由只解决“这是什么类型的问题”，没有同时解决“在哪个行业、哪个主体、哪种分析模式、需要哪些工具”。
- 我们的路由应拆成三层：
  1. 策略层：greeting / capability / analysis / report / abuse / out_of_domain / language_switch / clarify / refuse。
  2. 语义层：task_type + analysis_pattern + comparison_basis + subject_scope。
  3. 数据层：entity + industry_focus + province + metric filters + tool candidates。
- 显式上下文优先于粘性上下文：
  `本轮明确实体 > 本轮明确行业 > 上一轮行业焦点 > 历史话题 > 默认范围`
- “制造业的行业地位 → 那它的税负呢”应继承制造行业；“软件行业呢”必须覆盖为 IT 软件，不能继续沿用制造。
- 多行业问题不能只把所有行业混成一个聚合集。必须先按行业拆 worker，再生成确定性对比 Claim，最后汇总。

## 本轮后台实测

脚本：`backend/scripts/audit_intent_routing.py`

真实 HTTP 覆盖：

- 制造业的行业地位
- 批发零售的税票舞弊情况
- 制造业和软件的经营真实性对比
- 制造业的税负结构 → 那它的税负呢 → 软件行业呢
- 重新选范围后再次问制造业的行业地位
- 有哪些行业

验证目标：

- route 必须进入 `analysis`
- 行业焦点必须进入 `analysis_focus`
- 多行业对比必须保留两个行业，而不是只保留一个
- 换行业必须覆盖旧行业焦点
- 重新选范围必须清除旧行业焦点
- 每次分析必须有计划或确定性对比 Claim

实测结果：`passed=true`。8 个会话案例全部进入 `analysis`；多行业对比保留“制造 + IT软件”两个焦点，并生成确定性对比 Claim。完整输出见 `意图路由实测结果.json`。
