# 目标架构

## 一、总体形态

采用模块化单体，不拆微服务：

```text
backend/app
  api/                 HTTP 边界
  application/         用例编排
  domains/
    dialogue/          会话、SemanticPlan、LangGraph
    metrics/           指标、Claim、查询与校验
    reports/           报告计划、Block、渲染
    data_sources/      ETL、采集、来源注册
    identity/          认证、权限、邮件
  infrastructure/      DB、Redis、LLM、文件、对象存储
  shared/              极少量公共契约和错误类型
```

当前代码不需要立刻整体搬迁。先建立边界、门禁和 Facade，再逐块迁移。

## 二、业务模块

### Dialogue

职责：

- SemanticPlan。
- LangGraph 状态机和节点。
- 意图、焦点、话题记忆和回滚。
- 对话组合与响应组装。

不负责：

- 直接生成事实数字。
- 报告 PDF 渲染。
- 数据采集实现。

### Metrics

职责：

- 指标口径、查询、聚合、对比、排名、分布。
- Claim 生成和证据链。
- 规则校验和异常检测。

不负责：

- HTTP 路由。
- 报告模板。
- LLM 语言润色。

### Reports

职责：

- ReportPlan。
- 章节和 Block 组合。
- 报告质量检查、去重和可读性。
- PDF 渲染和数据打包。

不负责：

- 重新实现指标计算。
- 直接解析原始数据源。

### Data Sources

职责：

- ETL 和公开数据采集。
- Source Registry、文件版本和调度。
- 标准化事实输出。

不负责：

- 直接生成风险结论。
- 直接生成报告章节。

### Identity

职责：

- 登录、注册、JWT、权限。
- 邮件验证码和发送日志。

## 三、依赖方向

允许方向：

```text
api -> application -> domain
infrastructure -> ports
application -> ports
domain -> shared
```

禁止方向：

```text
domain -> api
domain -> infrastructure implementation
schemas/models -> services/api
api -> report renderer implementation
```

## 四、必须冻结的契约

- `SemanticPlan`
- `ToolSpec` / `ModuleSpec`
- `Claim` / `ClaimTrace`
- `ReportPlan` / `ReportBlock`
- `DomainPack`
- `DataSourceDescriptor`
- `CollectionTask`

契约冻结不代表永不变化，而是必须版本化、兼容和可回放。

## 五、Facade 优先

迁移巨石时先建立门面，不直接移动全部实现：

```text
judgment_service.py
  -> query_router.py
  -> aggregation_claims.py
  -> comparison_claims.py
  -> ranking_claims.py
  -> distribution_claims.py
  -> claim_factory.py
```

`judgment_service` 暂时保留为兼容 Facade，验证通过后逐项删除旧实现。

## 六、Strangler 迁移

采用渐进替换：

1. 新模块实现新入口。
2. 旧入口调用新模块。
3. 测试同时验证新旧输出。
4. 流量或测试完全切换后删除旧实现。

禁止一边迁移一边复制业务规则。
