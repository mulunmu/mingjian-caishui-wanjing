# 调研依据

调研结论不是要求立即拆微服务，而是采用模块化单体、渐进替换和自动门禁。

## 核心参考

### Shopify：Deconstructing the Monolith

https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity

关键结论：

- 大规模单体可以演化为模块化单体。
- 保留单代码库和单部署，同时定义并执行模块边界。
- 微服务不是所有单体问题的默认答案。

对项目的启示：当前应拆业务边界和依赖规则，不应立即拆服务。

### Martin Fowler：Strangler Fig

https://martinfowler.com/bliki/StranglerFigApplication.html

关键结论：

- 旧系统逐步被新能力替换，而不是一次性大爆炸重写。
- 新旧系统可以并存，直到新路径稳定并接管。

对项目的启示：`slice_report` 和 `judgment_service` 应以 Facade + 分阶段迁移方式拆解。

### Martin Fowler：Monolith First

https://martinfowler.com/bliki/MonolithFirst.html

关键结论：

- 早期系统不必提前拆成微服务。
- 边界只有在真实业务稳定后才更可靠。

对项目的启示：先做 Modular Monolith 和 Domain Pack，不拆分部署单元。

### Import Linter

https://import-linter.readthedocs.io/en/stable/

支持：

- Forbidden。
- Protected。
- Layers。
- Independence。
- Acyclic siblings。

对项目的启示：把“哪些模块不能互相引用”和“层级不能反向依赖”变成 CI 规则。

### dependency-cruiser

https://github.com/sverweij/dependency-cruiser

用途：

- 验证和可视化 JS/TS 依赖。
- 自定义禁止规则。
- 发现循环和越层引用。

对项目的启示：前端 `pages`、`components`、`stores`、`api` 之间需要自动规则。

### Modular Monolith with DDD

https://github.com/kgrzybek/modular-monolith-with-ddd

参考价值：

- 模块边界、模块契约和领域隔离。
- 模块内高内聚，模块间通过明确接口通信。

对项目的启示：Domain Pack 和领域 Facade 应该成为后续迁移出口。

### Thoughtworks：Architecture Fitness Functions

https://www.thoughtworks.com/insights/blog/architecture/evolutionary-architecture-fitness-function

关键结论：

- 架构属性应该被自动测量和持续验证。
- 依赖规则、性能、可靠性和可维护性都可以成为适应度函数。

对项目的启示：架构审计脚本、循环检测、文件大小棘轮和报告质量门禁都属于适应度函数。

## 最终方案

```text
模块化单体
+ Domain Facade
+ Ports / Adapters
+ Strangler Fig 迁移
+ Import Linter / dependency-cruiser
+ 架构健康基线
+ 版本化契约和审计回放
```

这是当前项目成本和收益最平衡的方案。
